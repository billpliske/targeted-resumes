---
name: update-personal-projects
description: Regenerate public/personal-projects-skills.md by reading the real code in the user's personal-project repos (GitHub, GitLab, Bitbucket, or any other git host — configured in the dashboard's Settings panel). Trigger on requests like "sync my personal projects", "update my personal projects skills file", "add my new repo to personal projects", or after the user has added/removed a repo URL in Settings.
---

Builds a verified, honest checklist of what's actually demonstrated in the user's public personal-project repos, for the `add-application`/`check-fit` skills to cite during tailoring. The whole point is that nothing in the output is guessed — every line traces back to something actually read in the repo's code, not a README claim or an assumption.

## Input

Read `public/settings.json`'s `personalProjectRepos` — a list of public repo URLs (GitHub, GitLab, Bitbucket, or any other host `git clone` can reach) the user maintains in the Settings panel (gear icon). If the list is empty, tell the user there's nothing to sync (and that they can add repos via Settings) and stop here.

## Steps

1. **Clone each repo fresh, don't trust a local checkout.** For each URL, `git clone` it into a scratch directory (not `/tmp` — use the session's scratchpad if one exists). Never read from an existing local checkout of the same project even if one exists on disk — a local working copy can silently differ from what's actually public (uncommitted changes, a different branch, a private fork), and employers only ever see the real public remote. If a clone fails (private, deleted, renamed, network error), note that plainly in your final report — don't skip it silently and don't guess at what it might contain.

2. **Read real code, not descriptions.** For each cloned repo:
   - Dependency manifests (`package.json`, `requirements.txt`, `Gemfile`, `go.mod`, etc.) for the actual frameworks/libraries in use.
   - Source files for concrete, resume-relevant technical patterns: notable integrations (payments, auth, email, analytics, AI/ML APIs), animation/CSS techniques, state management, testing setup, deployment/infra config, accessibility markup — whatever is genuinely there.
   - The README for context on what the project *is* (one line, for the summary list), but never as sole evidence for a technical claim — cross-check against the actual code before including anything sourced only from prose.
   - Note explicitly anything that's configured but not actually used (e.g. a test framework installed with zero test files) — call that out rather than claiming an active practice from it.

3. **Preserve what can't be re-derived from code.** If `public/personal-projects-skills.md` already exists, read it first and carry forward, verbatim, any "confirmed real but not in repo" facts the user has stated directly in a past conversation, and any genuine-gaps notes already recorded — these came from the user, not from code, and a fresh repo clone can't reproduce or invalidate them. Only change those sections if the user says so in this conversation.

4. **Regenerate the per-repo sections from scratch** using this conversation's fresh clones — don't patch the old file's per-repo bullets in place. This is what makes repo removal work correctly: a repo taken out of `personalProjectRepos` in Settings simply won't appear in the regenerated file, with no manual cleanup needed.

5. **Write `public/personal-projects-skills.md`**, matching this structure:
   ```markdown
   # Personal Projects — Verified Skills Reference

   Source of truth for what's genuinely demonstrated in the user's public repos — the ones actually linked from job applications when a posting asks for a code/portfolio URL. Employers can click through and inspect these directly, so nothing listed here should overstate what's really in them.

   - **<repo-name>** — <url> (<one-line description of what it is>)
   [... one line per repo ...]

   Verified by reading `package.json`/equivalent, source files, and docs directly — not from descriptions alone. Use this to check off job-posting keywords honestly during tailoring: if something isn't listed here and isn't in a job-history bullet in `original-resume.md` either, treat it as a real gap unless the user confirms otherwise directly.

   ## <repo-name> (<short description>)

   - <verified technical facts as bullets>

   [... one section per repo ...]

   ## Confirmed real but NOT in any repo (from the user directly, not from code)

   [carried forward from the previous file, per step 3 — omit this section if there's nothing here yet]

   ## Not present anywhere — genuine gaps, don't claim without asking first

   [carried forward from the previous file, per step 3 — omit this section if there's nothing here yet]

   ## Keeping this current

   Regenerated by the `update-personal-projects` skill from the repo URLs in Settings — re-run it (ask Claude Code) after these repos change meaningfully, or after adding/removing a repo in Settings, rather than hand-editing this file.
   ```

6. **Clean up.** Delete the scratch clones when done.

7. **Report back briefly.** Which repos were synced, one line per repo on what stood out, and call out plainly anything that failed to clone or looked worth flagging (e.g. a repo with almost nothing in it).
